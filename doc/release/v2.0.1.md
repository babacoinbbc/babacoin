# Babacoin Core V2.0.1 — Mainnet

Release Git tag: `v2.0.1`. Application/package version: `2.0.1`.
`RELEASE-MANIFEST.json` pins the exact source commit and packaged binaries.

This release improves responsiveness during header synchronization and makes
blockchain-file importing visible. The final build flag is enabled; the old
RC prerelease banner is absent. Existing synchronization and wallet warnings
remain enabled. Install the new package to replace an RC executable: changing
a GitHub release label cannot change a previously downloaded program.

## Install

Windows users should choose `babacoin-v2.0.1-windows-x86_64-setup.exe` and check
its `.sha256` file. The per-user wizard includes the required DLLs and Qt
plugins. Keep the portable archive together if using that alternative.
Windows ARM64 uses the tested x64 package under Windows 11 emulation.

Use the matching macOS Intel/Apple Silicon, Ubuntu LTS 18.04–26.04 or Debian
12/13 package. Raspberry Pi OS 64-bit uses its matching Debian ARM64 package;
physical Pi hardware and 32-bit operating systems are not certified.
See `PLATFORM-SUPPORT.md` for the actual validation levels.

## Responsiveness and progress

- Passive header/block display reads cached snapshots. A background worker
  retries busy validation locks instead of waiting on the GUI thread.
- Transaction history snapshots, batches, live updates and passive status
  painting retry busy chain locks. Deferred notifications are retained and
  replayed after validation releases the lock.
- Mempool and InstantSend statistics run outside the GUI thread. Large
  InstantSend database scans are skipped during initial synchronization.
- Initial balance display waits for the first successful balance snapshot.
  Sending remains unavailable until that snapshot exists; transaction creation
  and submission retain their normal fresh core checks.
- Header progress is explicitly an estimate. A recent header or a stale
  transaction estimate cannot mark unvalidated blocks as fully synchronized.
- Bootstrap importing reports actual file bytes read, new blocks indexed and
  a separate block-validation phase. File-read completion is not proof of full
  validation. Import state survives a GUI that attaches after importing starts.
- A Qt test fixture now releases its registered mock wallet on early failure.
  This avoids a subsequent duplicate database-handle assertion in the test
  executable. Assertions remain enabled.

The V2 day/night interface, localized amounts, startup rescan progress,
batched transaction history, optional Explorer peer discovery, Smartnode
wizard and external-browser Web Wallet tab remain available.

## Bootstrap

Download `bootstrap.zip` for genesis through block 1,062,893, or the incremental
archive only if the required base block matches. Verify `SHA256SUMS-BOOTSTRAP`.
After a clean shutdown, `bootstrap.dat` placed in the active mainnet data
directory is automatically imported on the next normal start. Alternatively,
use an explicit `-loadblock` argument. The incremental filename requires that
explicit argument unless deliberately renamed. See the included
`BOOTSTRAP-README.md` and the repository's bootstrap guide.

Normal proof-of-work, transaction and consensus checks still run. The supplied
sample-import report covers 1,000 blocks, not an independent replay of the
whole archive. Interrupted imports do not justify deleting wallets or chain
data. A `.old` filename alone does not prove validation finished successfully.

## Mandatory coordinated network upgrade

All validating wallets, exchanges, pools and nodes must upgrade **before the
first 2,000,000 BBC Smartnode registration**. Early registration has no opening
block. Unmodified V1 can reject the first such registration block.
The 1,800,000 BBC tier stops qualifying for rewards at block **1,250,000**.
Read `NETWORK-UPGRADE.md` and coordinate operators.

This maintenance update adds no further consensus transition, monetary rule,
key serialization or mainnet identity change. Its import observer reports
progress without deciding block validity. Installation does not move collateral,
register a Smartnode, submit a spork or upgrade other network participants.

## Validation and recovery

Release assembly requires the complete same-source platform matrix, including
core and Qt tests. Regression coverage holds the validation lock while checking
GUI heartbeats and the Hide action, and distinguishes header, file-read and
validation progress. Windows installer tests cover setup, startup, reinstall
and uninstall with wallet-preservation fixtures on x64 and ARM64 hosts.

Keep a verified wallet backup and read `MIGRATION.md`. Installing an executable
does not repair every historical wallet problem. No release can guarantee
that every device, historical wallet or network participant is defect-free.
